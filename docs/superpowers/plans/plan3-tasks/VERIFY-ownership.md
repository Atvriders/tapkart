### 0.0 PRE-FLIGHT BLOCKER — `content/` is not tracked by git

Verified in the repository, not inferred:

```
$ git ls-files content | wc -l
0
$ git check-ignore -v content/tracks/caldera.json
(not ignored)
$ git status --porcelain
?? content/
```

The entire `content/` directory — including the six shipped track JSON files from Plan 1 —
is **untracked**. It is not gitignored; it was simply never `git add`ed.

Consequence: **the plan cannot be executed in a git worktree.** Task 5 asserts (task-05.md:51-52)
*"The six track files (`content/tracks/*.json`) already exist in the repository and are not
generated by anything in Plan 3."* That is true of the working tree at
`<repo>` and **false of any worktree created from it**. In a worktree,
these fail immediately:

| Task | Failure |
|---|---|
| 5 | `tracks.ts`'s six static imports → `Cannot find module '../../../content/tracks/caldera.json'`; `tracks.test.ts`'s `readdirSync('content/tracks')` → ENOENT |
| 6 | `mkdir -p content/characters …` succeeds into an empty tree; the gate has nothing to compare against |
| 7 | `render-fixtures.ts`'s `loadShippedTrack` reads `content/tracks/*.json` with `node:fs` → ENOENT |
| 8 | every mesh assertion runs against the six real tracks via Task 7's fixture |
| 23 | `loadTrack('caldera')` in the golden fixture |

Task 6's `git add content/characters content/karts content/themes` would be the **first
`content/` files ever committed to this repository**, and would commit them alongside a
`content/tracks/` that is still untracked.

**Fix before Task 1: `git add content/` on master and commit it**, or run the whole plan in
the primary working tree. This is cheap to fix and total to ignore.

### 0.1 `buildTrackScene` has two incompatible signatures — Task 8 vs Task 22

Task 8 applies a **contract amendment** and says so openly (task-08.md:31-43):

> `TrackScene` therefore gains **`itemBoxes: Vec3[]`** … That forces one signature change,
> stated here rather than hidden: **`buildTrackScene` takes `ctx: SimContext` in place of
> `(track, query)`.**

Its shipped signature (task-08.md:148, 1286) is:

```ts
export function buildTrackScene(ctx: SimContext, theme: TrackTheme, opts: MeshBuildOptions): TrackScene
```

Task 22 was written against the pre-amendment surface. Its `Interfaces` block
(task-22.md:77-78) declares the old four-argument form, and its `shell.ts` calls it
(task-22.md:763):

```ts
buildTrackScene(loaded.track, loaded.query, loaded.theme, DEFAULT_MESH_OPTIONS),
```

`tsc --noEmit -p packages/game` fails: `Expected 3 arguments, but got 4` and
`Argument of type 'Track' is not assignable to parameter of type 'SimContext'`.
Task 22 has no test for `shell.ts` by contract (§8.2), so **`tsc` is the only thing that
catches this, and it catches it at the second-to-last task of the plan.**

Fix: in task-22.md, change the `Interfaces` declaration and the `startShell` call site to
`buildTrackScene(ctx, loaded.theme, DEFAULT_MESH_OPTIONS)` — `ctx` is already constructed
five lines above at task-22.md:737.

### 0.2 `TrackScene` is missing `itemBoxes` in Task 15 — same amendment, second casualty

Task 15 declares `TrackScene` **without** `itemBoxes` (task-15.md:90-97) and builds a
`TrackScene` object literal in `backend.test.ts` (task-15.md:209, `function trackScene():
TrackScene`). Under `strict`, a literal missing a required field is a compile error the
moment Task 8's amended `mesh.ts` is on disk.

Worse, Task 15 records the amendment as an *unfixed gap* it is deliberately not closing
(task-15.md:1092-1097):

> **Item boxes are not drawn.** `RenderFrame` carries `itemBoxAlpha` (Q29) but no item-box
> positions, and `TrackScene` (§4.3) carries none either … the cheapest fix is one
> `itemBoxes: Vec3[]` field on `TrackScene`, filled from `itemBoxWorldPos`, and it is a
> `mesh.ts` change, not this task's.

Task 8 already made that `mesh.ts` change. Task 15's "two honest gaps" commit message
(task-15.md:1200-1203) and its Q29 note are therefore **obsolete before they are written**,
and its three/renderer.ts leaves item boxes undrawn even though the positions are now
available.

Fix: add `itemBoxes: Vec3[]` to Task 15's quoted `TrackScene`, to the `trackScene()` test
helper, and either draw the boxes in `three/renderer.ts` or restate the gap honestly as
"positions are available; v1 does not draw them".

**Both defects trace to one root cause:** Task 8 amended a locked interface, said so
clearly in its own file, and the six authors who could not see task-08.md wrote against
the pre-amendment contract. Grep the whole set for `TrackScene` and `buildTrackScene`
before assembly; those are the only two consumers, and both are wrong.

### 1.1 HIGH — root `package.json` and `vitest.config.ts`: Tasks 1 and 23 make the identical edit

| Path | Task 1 | Task 16 | Task 23 |
|---|---|---|---|

Three tasks hold three different beliefs about who owns two files. Task 1 does the edit,
Task 16 says Task 23 will do it, and Task 23 does it again.

The edits are byte-identical, so nothing is destroyed — but the **RED steps disagree**,
and that is the real damage. Task 1's Step 3 expects, verbatim:

> `registers apps/* as a workspace…` → `AssertionError: expected [ 'packages/*' ] to deeply equal [ 'packages/*', 'apps/*' ]`

Run Task 23 first and Task 1's stated RED is unreachable, which under this project's own
rules means the RED was vacuous. Run Task 1 first — the correct order — and Task 23's
Step 1 silently rewrites two already-correct files with no assertion either way.

**Resolution: Task 1 owns both.** It is the only task with a *test* for them
(`packages/content/test/scaffold.test.ts` asserts `workspaces` deep-equals
`['packages/*','apps/*']` and reads the vitest config module to assert the include array).
Task 23 has no such test. Delete the two `Modify:` lines from task-23.md's `Files` block
and replace Step 1's two edit blocks with a verification-and-halt, in the style of Task 1's
own gate.

**Secondary damage:** Task 23's citation `package.json:6-8` is **stale by construction**.
After Task 1's edit the `workspaces` array occupies lines 6-9, not 6-8.

### 1.2 HIGH — `package-lock.json`: five writers, declared by none

`npm install` is run by Task 1 (Step 4), Task 7 (Step 3), Task 15 (Step 3b), Task 16
(Step 3e) and Task 23 (Step 2). Every one of them rewrites the root `package-lock.json`.

It appears in **no `Files:` block in the plan**. It appears in the `git add` of Tasks 1, 7,
15 and 16 — and is **missing from Task 23's `git add`** (task-23.md:682-686), so Task 23's

This also makes the whole plan **strictly serial across package boundaries**: five tasks

Fix: add `- Modify: package-lock.json (npm install side effect)` to those five `Files`
blocks, and add `package-lock.json` to Task 23's `git add`.
